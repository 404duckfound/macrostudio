# Macro Studio — agent notes

Tauri v2 + React 19 + Zustand + Vite 8 desktop app (Windows-first). Design tokens live in `src/theme.css`, mirrored by the `DESIGN.md` frontmatter hex values — keep those in sync when colors change. `DESIGN.md` has no prose body; it is tokens only.

## Commands (run in `macro-studio/`)

- Package manager is **pnpm** (`pnpm-lock.yaml`; no npm/yarn lock).
- Frontend verify: `pnpm build` (= `tsc && vite build`). **No frontend tests, no linter, no CI workflows exist.**
- Rust verify: `cargo check --manifest-path src-tauri/Cargo.toml` — keep it warning-free.
- Rust tests: `cargo test --manifest-path src-tauri/Cargo.toml` — **70 tests**, all inline `#[cfg(test)]` modules (most in `services/generator.rs`). Run them whenever you touch `generator.rs`, `ahk_manager.rs`, `watcher.rs` or the commands.
- Dev: `pnpm tauri dev` — Vite port `1420` is fixed (`strictPort: true`); `src-tauri/` is excluded from Vite watch (Rust changes recompile but don't reload the webview; config/capability changes need a full `tauri dev` restart).

## Backend layout (`src-tauri/src/`)

- `main.rs` is entry-point only; all wiring lives in `lib.rs` (`run()`).
- Modules: `commands/` (IPC `#[tauri::command]`), `services/` (`ahk_manager`, `generator`, `watcher`), `state/` (`AppState`). There is no `events/` module: the `active-window-changed` name is a string literal in both `watcher.rs` and `useTauriIpc.ts`.
- **New command = add fn in `commands/` + register it in `generate_handler!` in `lib.rs`** (forgetting this gives a runtime "command not found", not a compile error). If it touches fs/dialog/store/shortcut, also add the plugin permission in `src-tauri/capabilities/default.json`.
- IPC: request-response via `invoke` (see `src/hooks/useTauriIpc.ts` + components); backend→frontend events via `listen("active-window-changed")` — the name is a string literal in `watcher.rs`, keep it in sync with the `listen` call in `useTauriIpc.ts`.

## Gotchas (verified against current code)

- `tauri` dep needs `features = ["tray-icon"]` — without it `tauri::tray` fails to resolve.
- `state/mod.rs` re-exports `AppState`; commands import `crate::state::AppState`, not `crate::state::app_state::AppState`.
- `windows` crate is `0.58`: module is `Win32::System::Diagnostics::ToolHelp` (capital H — feature `Win32_System_Diagnostics_ToolHelp`); `MSG` is in `UI::WindowsAndMessaging`; null HWND is `HWND(std::ptr::null_mut())`; `app.emit` needs `use tauri::Emitter` in scope.
- `services/watcher.rs` shares the `AppHandle` via `static mut APP` + `std::ptr::addr_of!` — don't "simplify" to `APP.clone()` (hits `static_mut_refs` warning and breaks warning-free check).
- Saving a profile rewrites its `.ahk` but does NOT restart an already-running AHK process.
- `tools/AutoHotkey64.exe` **is in the repo** and bundled via `bundle.resources: ["../tools/*"]`. Locate it with `app.path().resolve("../tools/AutoHotkey64.exe", BaseDirectory::Resource)` — **never** `resource_dir().join("tools")`. The glob escapes `src-tauri/`, and Tauri's bundler encodes each `..` segment as a literal `_up_` directory, so the exe really installs to `<install>/_up_/tools/`. This is **documented, intended behavior**, not a bug (`tauri-utils/src/resources.rs`), and it applies to **both MSI and NSIS**. `resolve()` is the only API that reproduces it; joining paths by hand silently looks in a folder that never exists. The second candidate is `cwd/tools`, which is what makes `pnpm tauri dev` work (cwd = project root).
- Profiles/scripts are stored under raw `%APPDATA%/macro-studio/profiles` (JSON + `.ahk`) via `commands/profile.rs` — plain `std::env::var("APPDATA")`, not the Tauri path API. Windows-only assumption. `profile_save` always writes both `{id}.json` and the compiled `{id}.ahk`; `profile_list` backfills a missing `.ahk` for older profiles. Global macros live in `%APPDATA%/macro-studio/macros` (JSON only, no `.ahk`) via `commands/macros.rs` (`macro_list/save/delete`); triggers reference them by `{ type: "macro", macro_id }` and the generator expands the blocks inline at compile time.
- The overlay window, `OverlayPanel.tsx`, and the global-shortcut plugin were removed (dead code); tray menu is Exit-only. The Monaco-based `AhkEditor.tsx` was removed earlier along with the `@monaco-editor/react` dep.
- `tsconfig` is strict with `noUnusedLocals`/`noUnusedParameters` — unused imports fail `pnpm build`.
- **`Profile.enabled` no longer exists** (Rust struct + TS type). It was always `true` and only the window matcher read it; profiles written by older versions still load, because serde ignores unknown fields (`stale_profile_enabled_is_ignored` in `commands/profile.rs`).
- **App settings live in the Tauri store, not in `%APPDATA%/macro-studio/`**: `%APPDATA%/com.macrostudio.app/settings.json` holds `ignoredExes` and `focusFallbackMs` (default 750, exported as `DEFAULT_FOCUS_FALLBACK_MS`; the Settings reset button writes that same value).
- **`Ctrl+W` is not in `useKeyNav`'s `RESERVED` set.** WebView2 turns Close Tab / Close Window (`Ctrl+W`, `Ctrl+F4`, `Ctrl+Shift+W`) and F11 off unless the app handles `NewWindowRequested` (Microsoft's WebView2 "browser features" page), so reserving those chords only made the user's own trigger unreachable.
- **A duplicated trigger shortcut is a visible error, not a silent drop.** `cleanDraft` keeps the first card with a shortcut and omits later ones (the AHK output must never contain the same hotkey twice). The editor mirrors that filter in `draftDropReport` (`triggers/triggerDraft.ts`): the card gets a red "Duplicate shortcut" chip, the inspector shows the same red message a rejected Record/Picker combo gets, the profile header counts the cards a save would drop, and a save that drops cards says so afterwards ("Saved - 2 triggers were dropped ...").
- **The trigger drafts reset on a content change, never on object identity.** `useTriggerEditor` watches `JSON.stringify(active.triggers)`, not `active.triggers` itself: adding, duplicating or deleting a profile refreshes the list and hands over new objects with the same content. Resetting on identity wiped the unsaved edits and flipped `dirty` to false, so the `SwitchGuard` never asked and the profile switched away silently. A new profile goes through `onRequestSwitch` for the same reason — it switches away from the profile on screen.
- The keyboard map is one 15-unit row: every key is sized from `--key-gap` and its own `--w` with `calc()`, so columns line up across rows and the map fills the canvas. Mouse buttons are a separate `MOUSE_KEYS` list in `lib/keyboardLayout.ts` rendered in the side column next to the mouse-trigger mini list.
- **Layers (G-Shift style) live in the profile.** `Profile.layers: [{ id, name, activator }]` plus `Trigger.layer` (a layer id, `None` = the normal layer); both fields are `#[serde(default)]`, so existing profiles load and compile unchanged. The compiler emits a layer's triggers as AHK `HotIf` variants, and AHK's global variant always has the lowest precedence — while the activator is held, the layer wins and the normal trigger stays silent.
- **Three AHK rules the layer generator depends on** (all verified against the bundled AutoHotkey v2): a hotkey callback must take one parameter (`Fn(HotkeyName)`; a parameterless one is rejected with "Invalid callback function"), the `Hotkey` action must be the function itself and not its name in quotes (a quoted action looks up a hotkey *label*), and a modifier activator (Shift/Ctrl/Alt/Win) has to be part of the layer's hotkey name — AHK does not fire a plain `p` hotkey while Shift is held.
- **Layers are managed in the profile modal** ("Layers" section: name + activator + remove; the activator is a single key, because AHK can only read one key's physical state). The trigger picks its layer in the inspector's "When" step, and the card shows the layer name as a badge. A trigger whose layer was deleted falls back to the normal layer in the compiler — it must never fall out of the script.

## Frontend conventions

- Shell: `App.tsx` = `TitleBar` on top (frameless, 38px, logo + white title text left, min/max/close right, 1px bottom border, needs `core:window:allow-*` permissions) and, **inside it**, the `Navbar` (Profiles / Macros / Settings as horizontal pills, absolutely centered by `.titlebar-center`). Below is one view per nav item: `profiles/ProfilesView.tsx`, `macros/MacrosView.tsx`, `settings/SettingsView.tsx`. **There is no side rail** — the profile and macro lists were replaced by `SelectMenu` popovers in the canvas header, so profile selection, add/edit/duplicate/make-default/delete and the engine status dot all live in `profiles/ProfileHeader.tsx`.
- `components/` is grouped by **screen**, then by role within a screen: `common/{chrome,ui}` (chrome = app shell, ui = reusable controls), and one folder per view (`profiles/`, `macros/`, `settings/`) holding everything that view renders. In `profiles/`: `actions/` (action editors), `triggers/{list,inspector,fields}/`, `modals/`, plus the view and its header. The naming rule is "who renders it" — `BlockRow` lives in `macros/` even though it renders a trigger block, because `MacrosView` is its only consumer.
- **Closing the main window hides it to the tray** (`on_window_event` → `WindowEvent::CloseRequested` → `prevent_close()` + `hide()`); AHK keeps running. Real quit is the tray's `Exit`, which is the only path that fires `RunEvent::Exit` and therefore `AhkProcessManager::stop_all()`. Window is restored by the tray's `Show Macro Studio` item **or** a left double-click on the tray icon; the single-instance plugin's focus callback reuses the same `show_main_window()` helper.
- `ProfilesView` layout: canvas header carries the profile `SelectMenu` (name + default star + engine dot + scope) with the List/Keyboard tabs pinned right; the "Unsaved changes" indicator sits on that same row, right of the select. A warning line below the header appears only when a draft card would be dropped on save (no action, no shortcut, duplicate shortcut). Trigger cards are icon + modifier badges + kbd chips; `Add new trigger` is the dashed button under them. The 400px right dock (`.inspector`) holds the step cards: When → Modifiers → Action.
- **The canvas keyboard map has two input paths.** A *physical* press navigates to an existing trigger or opens a card with the full combo; a *map click* on a key that no trigger uses opens the modifier mini picker (`KeyModifierPicker` in `profiles/KeyMatchPicker.tsx`) and always adds a new card — it never rewrites an existing one. Both paths keep the canonical key spelling: the generator matches `MouseLeft` exactly, so lookups may uppercase but written combos may not.
- The trigger card's "..." menu and the profile option menu are the same floating panel (`.rail-menu` + `.rail-menu-inline`, fixed position from the button's rect) with Lucide icons on every item. The card menu holds Duplicate + Delete only; blocking the original key lives in the inspector's Modifiers step.
- **Profile switching is gated.** `useTauriIpc` never writes `activeId` for a window match or the pinned fallback; it queues the request in the store (`requestSwitch`). `SwitchGuard` applies it — immediately when the view is clean, otherwise after Save / Discard / Cancel. An unanswered request is applied on unmount so it cannot get stuck. A manual switch also sets `pinnedId`; an automatic one must not, or the 750ms pinned fallback can never win. Notifications fire on `lastSwitch` (the switch that actually landed), not on the request.
- Profile semantics: `target_exe: null` = applies to **all** windows; the add/edit modal owns the target-exe picker (visible windows via `system_visible_window_exes`/EnumWindows or active-window capture); each trigger carries its own shortcut + actions, edited in the `ProfilesView` inspector.
- `defaultId` (default-profile selection) is **frontend-only Zustand state, deliberately not persisted** — `useTauriIpc.ts` self-heals a `Default` all-windows profile (`target_exe: null`) at startup and whenever the last all-windows profile is deleted; explicit "Make default" on a targeted profile is never overridden.
- Global `contextmenu` is suppressed in `main.tsx` (right-click menus intentionally disabled).
